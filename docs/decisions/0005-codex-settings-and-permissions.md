# 0005 · Codex settings and permission modes

Discover text models through the installed Codex App Server catalog and
present the reported effort options. Verify a selected model and effort
again when opening its fresh run. If a requested choice has disappeared or
Codex reports a different setting, fail before submitting the turn. Store
requested settings with the queued input and effective model and effort
when Codex confirms them. Legacy records can have unknown requested values.

Ask uses the Codex read-only sandbox, disables tool network access, and
declines escalation. Agent requests workspace-write with the recorded
project root and routes escalation to the user. Neither mode extends
writable roots to the system temporary directory. Read access follows
Codex's Linux sandbox policy. The model service connection remains
available for responses.

Scoped clients use per-process overrides for hooks, apps, plugins, web
search, subagents, and other extension entry points. If effective
configuration lists an enabled MCP server, reopen with an explicit disable
override for each server and verify the result before starting a thread.
An empty MCP table alone leaves inherited servers enabled. The overrides
leave the user's CLI configuration and sign-in intact. ResOS's explicitly
enabled notebook lookup stays available through its scoped callback.

Retry retains the original input and settings. If a requested model or
effort was left to the harness, retry pins the effective value when
recorded. A separate action uses the current settings while keeping the
original input. Changes to the workspace root still need confirmation.
